install and setup

One binary. One budget. Then stop waiting.

Install pkgcache, tell it how much disk it may use, and run your normal commands through it. It starts when something needs it, sleeps when nothing does, and keeps every package it has already fetched.

Three commands Explain each one

No sudo for the cache itself, no certificate, no account, and nothing another machine can reach.

first, for every platform

Get pkgcache

Choose your buildinstallers + 5 targets

Linux

The .deb pair installs the daemon and the desktop half together; apt resolves the GTK dependencies.

  1. Install

    sudo apt install ./pkgcache_*_amd64.deb ./pkgcache-desktop_*_amd64.deb

    No desktop? The first package alone is a complete daemon and CLI.

  2. Give it a budget

    pkgcache setup -limit 25G

    Mandatory. Without a number it refuses to start.

  3. Use it

    pkgcache run -- pip install numpy pkgcache run -- npm ci pkgcache shell

  4. Docker

    pkgcache pull python:3.12-slim pkgcache build -t app:dev .

    Your Dockerfile is not modified. Add -print to see the rewrite and build nothing.

  5. Optional — a team cache in front

    pkgcache setup -server https://cache.example.com:8443 -ca-sha256 "PASTE_FINGERPRINT"

    The fingerprint comes from whoever runs it. See Team cache.

macOS

The .pkg installs a universal binary, the app and the docker shim, and symlinks all three into /usr/local/bin.

  1. Install

    sudo installer -pkg pkgcache-*.pkg -target /

    Or double-click it. On an unsigned build, open it from the right-click menu once.

  2. Give it a budget

    pkgcache setup -limit 25G

    The installer sets one already; this changes it.

  3. Use it

    pkgcache run -- pip install numpy pkgcache run -- npm ci pkgcache shell

  4. Docker

    pkgcache pull python:3.12-slim pkgcache build -t app:dev .

    Docker Desktop runs in a VM. pkgcache build works that out for you — see Docker.

  5. Optional — a team cache in front

    pkgcache setup -server https://cache.example.com:8443 -ca-sha256 "PASTE_FINGERPRINT"

step 1

Every file, for every platform.

Two channels. The tagged release is what you want: a fixed version, checksummed, with provenance you can verify. The build from main is the newest merge, for when you need a fix before it is tagged. Both are currently unsigned — there is no Apple or Windows signing identity behind them — so macOS and Windows will each want convincing on first run, and the commands below say how.

SHA256SUMSverify first
Verify before you run. Every release ships SHA256SUMS over everything in it. Download it beside the file and check: sha256sum --ignore-missing -c SHA256SUMS, or shasum -a 256 --ignore-missing -c SHA256SUMS on macOS. This is worth the ten seconds on an unsigned build, where nothing else vouches for the bytes.

Which file do I want?

  • An installer if this is your own machine — it carries the daemon, the app and the docker shim together.
  • pkgcache-<os>-<arch> for a CI runner, a container image or a server: one static binary, no dependencies.
  • install.sh to script it, including on a machine that should be pointed at a team cache as it installs.
  • pkgreg-linux-* only if you are setting up the team's cache rather than your own.

Or build it

Nothing here needs a release. The client is one Go package with no cgo.

git clone https://github.com/aabdlwahab/PKGCache.git cd PKGCache/go && make pkgcache

Or go install github.com/aabdlwahab/PKGCache/cmd/pkgcache@latest. The desktop app is the one part that needs a toolchain — GTK4 and WebKitGTK on Linux, Xcode's on macOS.

step 2

Install it, then name a budget.

Two commands, and the second one is the only decision. After that the cache starts itself whenever something asks for a package, and exits when nothing has for a while.

  1. 1

    Put the binary somewhere on PATH

    An installer has already done this. If you took the raw binary, it is two commands — and on macOS, move it into place rather than writing over an existing copy: a code signature is cached against the file's inode, and overwriting the bytes of a running binary's file leaves later runs killed by the kernel with no message but killed.

    chmod +x pkgcache-linux-amd64 sudo install -m 0755 pkgcache-linux-amd64 /usr/local/bin/pkgcache

    Windows: put pkgcache-windows-amd64.exe in a folder on PATH and rename it pkgcache.exe.

  2. 2

    Tell it how much disk it may use

    This is mandatory, and deliberately so. A cache with no ceiling grows until the disk is full, and the machine it was supposed to speed up stops working entirely. Give it a number and it will stay under it.

    pkgcache setup -limit 25G

    Change it later with pkgcache limit 40G, or pkgcache limit none if you genuinely want no ceiling. Add -min-free 10G to keep a floor of free disk underneath the budget, which is what you want on the partition your builds also write to.

  3. 3

    Run something through it

    pkgcache run sets the variables the tools read, runs one command, and puts the environment back. Nothing is written to your project, your home directory or the operating system.

    pkgcache run -- pip install numpy

    The first run fetches from upstream and keeps what it fetched. Run it again in a fresh virtualenv and watch where the time goes.

    pkgcache status

What that actually changed

A directory, and nothing else. No system files, no certificate store, no service running as root, and no port another machine can reach — pkgcache refuses to bind one. Print the environment it hands your tools at any time:

pkgcache env
  • PIP_INDEX_URL, UV_DEFAULT_INDEX, NPM_CONFIG_REGISTRY — why pip, uv and npm need no flags
  • GIT_CONFIG_COUNT and friends — an unmodified github.com clone, redirected through the mirror
  • PKGCACHE_APT_PROXY — the plain-HTTP proxy apt and apk use
  • PKGCACHE_FILES_URL, PKGCACHE_DOCKER_REGISTRY — artifacts, and the image registry covered under Docker

To keep those settings in a shell that outlives one command, use pkgcache shell, or eval "$(pkgcache env)". To make them survive a reboot, pkgcache persist.

step 3

Use normal package commands.

Inside pkgcache run or pkgcache shell, every one of these is the command you already type. The cache is on loopback, so there is no certificate anywhere in the path and nothing to add to a config file.

Python

pip

pkgcache run -- pip install numpy
Python

uv

With a lock file, pkgcache warmlock fills the cache from it and points the lock at the cache.

pkgcache run -- uv sync --locked
Node

npm, yarn, pnpm

pkgcache run -- npm ci
Source

Git

The URL does not change. Submodules and pip install git+https://… are redirected with it.

pkgcache run -- git clone https://github.com/pallets/click.git
System

apt and apk

Here sudo is for changing operating-system packages, not for pkgcache.

sudo apt-get -o Acquire::http::Proxy="$PKGCACHE_APT_PROXY" update
Artifacts

Files

Anything with a URL and no package manager behind it — model weights, toolchains, your own build outputs.

pkgcache run -- wget "${PKGCACHE_FILES_URL}builds/v1.2/app.tar.gz"
Do not add TLS workarounds. No --trusted-host, no --insecure, no CA path. The cache answers plain HTTP on your own loopback interface, so every such flag removes a check that was not in the way. If a tool reports a certificate error, it is talking to something else — see Troubleshooting.
A command that is not in this list? pkgcache shell puts the same variables in an ordinary child shell, so anything that reads the environment — a Makefile, tox, a script, your editor's terminal — picks them up with no per-tool work.

step 4

Docker plays by different rules.

Every other tool reads your shell. The Docker daemon does not — it is a separate process, often in a virtual machine with its own idea of localhost. So pkgcache drives docker for you rather than asking you to configure it.

  1. A

    Pull an image, keeping its name

    A pull through a cache normally means retagging: you ask for 127.0.0.1:41780/dockerhub/library/python:3.12-slim and live with an image whose name is an address. pkgcache pull fetches through the cache and then gives you back the name you asked for.

    pkgcache pull python:3.12-slim pkgcache pull ghcr.io/astral-sh/uv:0.10.8

    Any registry works by naming it — ghcr.io, quay.io, nvcr.io, gcr.io — with nothing configured first.

  2. B

    Build an image

    pkgcache build takes the same arguments docker build does. It rewrites a copy of your Dockerfile in memory and hands that to docker on stdin; the file on disk is never touched.

    pkgcache build -t app:dev . pkgcache compose build

    What it changes, and nothing else:

    • Build arguments for the tools that read them — PIP_INDEX_URL, UV_DEFAULT_INDEX, NPM_CONFIG_REGISTRY, the Git ones, and http_proxy for apt and apk. ARG, never ENV: an image that ships someone's laptop address is broken the moment it leaves that laptop.
    • FROM lines, for any registry the reference names. A registry only this machine can reach — localhost:5000, an address, a host:port on the build network — is left alone, because it means something different where the cache runs.
    • The # syntax= directive, which names the frontend BuildKit parses the file with and is fetched before the first instruction is read. A build whose every FROM came from the cache would otherwise still go to Docker Hub for that one, first.
    • A borrowed image — COPY --from=ghcr.io/astral-sh/uv:0.10.8 or a mount's from=. A stage name or a stage index is left alone; it has no registry to be fetched from.
    • One RUN, only in a stage that runs apk, moving its repositories to plain HTTP so the proxy can see them — and putting them back before the stage ends.
    pkgcache build -print .

    Prints the rewritten Dockerfile and every substitution, and builds nothing. Worth running once on a Dockerfile you know well.

  3. C

    Builds you start some other way

    A Makefile, an IDE, a CI script, docker compose up — anything that calls docker itself cannot be wrapped. Two one-time commands cover those.

    pkgcache docker-setup pkgcache docker-build-setup

    The first teaches the Docker daemon about this cache, so docker pull against it works from anywhere on the machine; add -mirror and even an unmodified docker pull python:3.12 is served from the cache, which is off by default because it reroutes every pull on the machine. The second sends apt and apk through the cache in every build on this machine, whoever started it.

Docker Desktop, and any remote builder. On macOS and Windows the daemon lives in a VM where 127.0.0.1 is not your machine, and a RUN step is in its own network namespace even on Linux. pkgcache build works out an address the daemon can actually dial and passes it in, which is why it is a wrapper rather than a page of instructions.

step 5 — optional

Put your team's pkgreg behind it.

A team cache is pkgreg: the same engine run as a host other machines point at. Tell pkgcache about it once, and a package this machine has never seen is asked of the team before it is asked of the internet. Nothing about your commands changes — they were already pointed at loopback.

your team cache

Paste the address you were given and every command on this page will use it. It is remembered in this browser and sent nowhere.

examples use the placeholder address

  1. 1

    Get the fingerprint from whoever runs it

    A team cache serves TLS from its own CA. pkgcache fetches that CA over an unverified connection and then refuses it unless it matches a fingerprint you were given separately — which is exactly the check that would catch someone impersonating the cache, so it is the one thing you cannot skip. Ask for it over a channel you trust; it looks like AA:BB:CC:….

  2. 2

    Point this machine at it

    pkgcache setup -server https://cache.example.com:8443 -ca-sha256 "PASTE_FINGERPRINT" -limit 25G

    That is the whole change. It writes two ordinary upstream rows per index — the team at priority 10, the public registry at 20 — and the engine walks the chain it already knew how to walk.

    Have the CA file itself instead of a fingerprint? -ca-file ./ca.crt takes it and derives the fingerprint from it.

  3. 3

    Check the chain

    pkgcache status

    All three tiers for the current project, with the team cache probed — so one that has been down for a week shows as down, rather than as "builds got slower".

What happens when the team cache is unreachable

The next origin is tried: on a connection refused, a DNS failure, a timeout or a 5xx. Deliberately not on a 404 — that is what a cache in offline mode answers, and falling through would defeat it — and not on a 401 or 403, which is a credential problem that going around would hide.

Never fetch from the internet myself

-no-direct omits the public row entirely, so this machine reaches upstream only through the team. It holds even for a registry nobody configured, because a discovered registry is chained through the team's own /v2 root.

pkgcache setup -no-direct
Projects, a client with no local cache, and undoing it

One project at a time

-project work configures the chain for one of this machine's projects, and -team-project names the project on the team's side — which defaults to their global project, because assuming a name exists on somebody else's server is not this program's call. A project with no configuration of its own inherits the global one, and pkgcache project ls marks an inherited chain with *.

pkgcache setup -project work -server https://cache.example.com:8443 -ca-sha256 "PASTE_FINGERPRINT" -team-project platform

A pure client, with no cache of its own

-no-cache is the old pkgreg-client exactly: a verified loopback bridge to the team cache, with nothing stored locally. Nothing is written to the cache directory and no database is opened. Use it on a shared host, or where the disk is not yours to spend.

pkgcache setup -no-cache -server https://cache.example.com:8443 -ca-sha256 "PASTE_FINGERPRINT"

Forget it again

Removes the team cache and its chain, including the CA that came with it. Your local cache and everything in it stay.

pkgcache setup -uninstall
Chained ecosystems are pypi, npm and OCI. apt and Git work out their origin from the request itself rather than from configuration, and files has no upstream at all — its content arrives by upload. Those three are absent from the chain rather than half-supported.

projects, checkpoints, and no network

Name what works. Carry it somewhere else.

Every project keeps its own cache. You can name what one holds right now, come back to that name later, and move the whole thing to a machine that has never had a network.

Projects

One per piece of work, so a checkpoint means something. A command uses the project you last selected.

pkgcache project create work pkgcache project use work pkgcache project ls

Checkpoints

Record what this project holds, without stopping anything, and return to it after the upstream has moved on.

pkgcache checkpoint "green build" pkgcache snapshots pkgcache rollback "green build"

Onto a machine with no network

On the machine that has one, write a pack. On the one that does not, import it.

pkgcache export -o work.pack pkgcache import work.pack

A second trip carries only what is new. Afterwards the tools are configured exactly as they were — they simply never leave the disk, and an uncached dependency fails clearly instead of hanging on a network that is not there.

troubleshooting

When something does not work.

a disk budget is required

pkgcache will not start without one, on purpose. Run pkgcache setup -limit 25G, or pkgcache limit none if you really do want it unbounded.

CA fingerprint mismatch

The certificate the team cache served does not match the value you passed. Stop and confirm the fingerprint with whoever runs it, over a channel you trust. This is the check that would catch an impersonated cache, so do not work around it.

server must use https

A team cache is only accepted over HTTPS. An http:// address means the instance has no certificate pair yet — that is a fix on their side, not a flag on yours.

A tool ignores the cache and goes upstream

It is not reading the environment. Check with pkgcache env, and remember that a tool started outside pkgcache run or pkgcache shell — an IDE, a daemon, a login shell opened earlier — has the old environment. pkgcache persist is the answer for the ones you cannot wrap.

connection refused inside docker build

A RUN step runs in its own network namespace, where 127.0.0.1 is the build container and not your machine. Use pkgcache build, which works out an address the daemon can dial rather than assuming loopback.

A FROM line was not rewritten

Run pkgcache build -print . — every substitution is printed, and a line that was left alone was left alone for a reason: a variable in the image name, an image this machine already has locally, or a registry only this machine can reach.

It filled up

Nothing is ever deleted without your say-so. pkgcache prune reclaims space when you ask; pkgcache limit changes the ceiling; -min-free keeps a floor of free disk underneath it.

How do I undo all of this?

pkgcache setup -uninstall forgets a team cache. pkgcache stop stops the daemon. Beyond that, deleting the cache directory is the uninstall — nothing was written anywhere else. On macOS the .pkg also installs pkgcache-uninstall, which removes the bundle, the symlinks and the login item.
