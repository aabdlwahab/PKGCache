[pkgcache]

A package cache for the machine you are sitting at

One loopback port. No certificate, no account, no privileged setup. The first command that needs it starts it, it exits when nothing has used it for a while, and the next command starts it again. This is how to use it — every command, with the output it actually produces.

Ordered — each step needs the one before it

First five minutes

Three commands, and the third one is the only one you keep typing.

  1. Get the binary

    One static executable with no runtime dependencies. Build it, or copy a release binary onto the machine — including a machine with no network, which is the point of the last section on this page.

  2. Tell it how much disk it may use

    It asks once and never guesses. A server evicts; this does not — the packages in it are the ones your current work depends on, and a background process deleting them to hold a number nobody chose is the wrong behaviour on a machine you are sitting in front of.

    pkgcache limit none means no cap — a free-disk floor still applies. PKGCACHE_LIMIT=25G is the same answer for CI, where nobody is there to be asked.

  3. Run something through it

    run is the verb to remember. It starts the cache if it is not running, points pip, uv, npm, yarn, pnpm and git at it, runs your command, and leaves nothing behind — no config file edited, no certificate installed, no --trusted-host.

    Run it again and the packages come off your disk. That is the whole product; everything below is a way of seeing it, sharing it, or carrying it somewhere else.

Two more shapes

pkgcache shell opens a child shell with the same settings — type exit to return. eval "$(pkgcache env)" prints the exports for a shell that has to keep them.

A window, not a tab

The window

Nobody keeps a browser tab open to watch a cache. pkgcache widget opens a small window — no tabs, no address bar — that answers four questions in one column: is the cache working, how much room is left, is it actually helping, and what is it doing right now.

A Chromium-family browser (Chrome, Chromium, Edge, Brave) gives the window without tabs; anything else gets an ordinary one and pkgcache tells you which you got. Over SSH, where there is no browser to open, it prints the address instead of failing. -on-login writes exactly one marked file under your home, and -off-login removes it.

It watches; it does not hold

The window never keeps the daemon alive. When the cache goes idle it exits as usual, and the window reads the last figures from disk until something needs it again.

The same projects a server has, minus the accounts

Projects

There is one person here and nobody to keep out, so a project on a laptop is exactly two things: a separate upstream chain — work resolves through the company's cache while a side project goes straight to the public registry — and a separate accounting boundary, so "what is this project costing" is a question with an answer.

The * is where you are working. The second column is where a miss goes next, and ↑ means that project is following the global project's chain rather than one of its own.

Not an isolation boundary

Content is stored once by digest and shared, which is the point — two projects that need the same 2.5 GB wheel hold one copy. Deleting a project drops its catalog entries and leaves the bytes for pkgcache prune to reclaim when nothing references them. Nothing should be built on the assumption that a project hides anything from another.

Three tiers, and it is a chain rather than a mode

A team cache in front

With a team cache configured, a lookup goes local, then the team's cache, then the registries. Setup writes two ordinary upstream rows per index — the team at priority 10, the public registry at 20 — and the engine walks a chain it already knows how to walk. The team's CA is fetched over an unverified connection and refused unless it matches the fingerprint you were given separately; every request after that is verified normally.

pkgcache status probes the team cache every time you ask, so one that has been down for a week is visible rather than just "builds got slower":

Per project, and two ways to say no

  • setup -project work -server … gives one project its own team cache. A project without one inherits the global project's, so a machine pointed at a team cache routes everything through it until told otherwise.
  • -team-project names the project on their side. It defaults to their global project, because assuming a name exists on somebody else's server is not this program's call.
  • -no-direct omits the public row, for a machine that must never fetch from the internet itself.
  • -no-cache stores nothing at all: a verified loopback bridge to the team cache and no local database. This is what the old pkgreg-client did, and it is still one flag.

Fall-through happens on a refused connection, a DNS failure, a timeout or a 5xx — deliberately not on a 404, which is what a cache in offline mode answers, and not on a 401 or 403, which is a misconfigured credential that going around would hide. Chained ecosystems today are pypi and npm.

Your Dockerfile is never modified

Docker builds

build and compose rewrite the Dockerfile in memory and write the generated file outside the build context, so a COPY cannot pick it up. Anything pkgcache does not recognise is passed to docker untouched.

Both machine-touching commands take -dry-run and -uninstall, and neither will overwrite an entry you wrote yourself.

For the tools that never see your shell

Settings that stay

run and shell cover the case where somebody types pkgcache. persist covers the rest: a Makefile, an IDE, a colleague's script, a terminal opened before anybody thought about caching. It writes user-level files only — no root, nothing under /etc, no machine-wide trust store — each fenced by markers so -uninstall removes exactly what was installed.

Why it installs a socket too

Settings that outlive the process they point at are the one way this design could leave a machine worse than it found it: a .npmrc naming a port nothing is listening on fails npm rather than slowing it. So persist installs socket activation — systemd or launchd holds the port open, the cache still exits when idle, and the address always answers. Where there is no socket activation it refuses unless you pass -anyway.

A plane, a customer site, a room with no network

Carrying it offline

The packages you need in order to keep working while disconnected are the ones already in your cache — that is what it is for, and why it never evicts. So the client can hand them over: a pack is a tar carrying a manifest and the blobs it names, and it moves in any direction between any two instances.

export checkpoints the project first, so the pack is what the cache holds now rather than what it held the last time somebody thought about it. import applies the pack as it reads it — there is no second command — and creates the project if the receiving machine does not have it.

The second trip carries only what is new

The * marks the checkpoint the project is on — the one fact both ends of a transfer need. There is no default for -since on purpose: only the receiving machine can say which checkpoint it has, and a delta whose base the far side lacks is refused rather than merely slower.

An import cannot lose what you already have

A pack records where it started, and it is refused unless that matches the receiving project's checkpoint. Nothing is written on refusal, and the message says what to do about it:

The one command that does replace a project's content is pkgcache rollback <checkpoint>, which says so in its own help. Packs are verified against the digests they name, which catches corruption — it says nothing about who made one.

Both buttons are in the window too

Export a pack checkpoints and writes one, then shows you the path. Import a pack applies the pack waiting in this cache's shuttle/in — copy it off the stick with your file manager, then click.

The failure that would otherwise be silent

When it fills up

At the limit the cache keeps serving and stops storing. Your build still works; it is just no longer being made faster. A cache that silently degrades is worse than one that fails, so this is reported four ways and none of them is the only one.

ChannelWhat you see
stderrafter run and shell, in the terminal you were already watching
pkgcache statusa CACHE FULL line, and a non-zero exit
desktop notificationonce an hour at most, skipped where there is no desktop
exit status 75from every command, run included

75 is EX_TEMPFAIL, and no package manager returns it — so "the build failed" and "the build worked and nothing was cached" can never be confused. A failing command's own status always wins, because the build failing is the more urgent of the two facts.

Nothing outside this directory

Where things live

PKGCACHE_DATA_DIR moves all of it. The only files written anywhere else are the ones persist, docker-setup, docker-build-setup and widget -on-login install — each marked, each reversible with -uninstall or -off-login, and none of them will touch something you wrote yourself.

The one thing this does not promise

A loopback socket is not per-user. Any account on this machine can reach the cache and its API, and pkgcache says so in its own log at every start. It serves with no certificate and no accounts, which is safe exactly as long as nothing off this machine can connect — so it refuses to bind an address that anything else could reach. For a cache other machines use, run pkgreg serve.

Every command and every screenshot on this page is real output from pkgcache, captured on Linux. The macOS and Windows branches of docker-setup, persist, the login entry and the desktop notification are written to the same contract and compiled for all three platforms — they have not been run.
