the problem

This machine downloads the same packages over and over.

A fresh clone, a rebuilt container, a colleague's branch, a CI job on the box under your desk — each one pulls the wheels, the tarballs and the base images that are already on this disk, and each one waits for them.

Download pkgcache Read the tutorial

One static binary, one command to set up, and a disk budget you choose. No certificate, no account, nothing that needs administrator access.

the waiting

The same bytes, every build

A multi-gigabyte CUDA image and a 300 MB wheel do not get faster the fourth time you fetch them.

the sprawl

Six tools, six ways to configure

pip has a variable, npm has a file, apt has a proxy, Docker has a daemon. Setting all of them up by hand is a morning nobody has.

the wall

On a plane, nothing installs

Away from the network an uncached dependency stops the work, even though the package sat in a directory two builds ago.

one cache, every ecosystem

Fetch once. Everything after that is local.

pkgcache runs on this machine and answers on one loopback port. Point a tool at it — or let pkgcache run point it for you — and the first request is fetched and kept. Every request after that is served off this disk.

01

Local after the first fetch

An artifact is stored the first time anything asks for it, and served from disk to everything that asks afterwards.

02

Nothing privileged, nothing permanent

No TLS certificate, no account, no daemon that has to run as root. It refuses to bind an address another machine can reach.

03

One process for the whole build

Containers, Python, Node, apt and apk, Git and plain files come out of one binary and one directory.

LOCALcached artifact → served from this disk, at loopback speed
ONCEuncached artifact → one upstream fetch, shared by everything waiting
VALIDan interrupted download is never committed as cached content

what a project holds

Name what works today. Come back to it in March.

Every project keeps its own cache. Checkpoint one while it is running, and that name is a state you can return to — the same content, the same versions, after the upstream has moved on.

built for the machine with no network

Carry the cache. Keep building.

Export a pack on the machine that has a network, carry it however your rules allow, and import it on the one that does not. The tools are configured exactly as before; they simply never leave the disk.

  1. moveCarry the packA single verified file on approved media or an internal transfer path.
  2. importLoad it thereImport on the disconnected machine and start the cache offline.
  3. serveBuild cache-onlyCached dependencies resolve normally. An uncached one fails clearly instead of hanging on a network that is not there.

Six ecosystems · one binary

One cache for the tools you already type.

All six roles answer on one loopback port — 127.0.0.1:41780 by default, the apt and apk forward proxy included. pkgcache run and pkgcache shell set the variables each tool reads, so the commands below are the ones you already know. Docker is a separate daemon that cannot read your shell, so it has its own section in the tutorial.

containersany registry, by name

Container images

Pull and build through the cache. Any registry works by naming it — Docker Hub, ghcr, quay, nvcr.io — with nothing configured first.

$ pkgcache build -t app:dev .
pythonpip · uv

Python packages

Fetch a large wheel once. Every later install, in every virtualenv on this machine, is a local copy.

$ pkgcache run -- pip install numpy
nodenpm · yarn · pnpm

Node packages

A cold node_modules stops being a network operation, and keeps working with the network off.

$ pkgcache run -- npm install
systemapt · apk

System packages

Debian, Ubuntu and Alpine packages through one plain-HTTP forward proxy — in a shell, or in every container build on this machine.

$ pkgcache docker-build-setup
gitread-only mirrors

Git repositories

An unmodified github.com clone is redirected through a local mirror — submodules and pip install git+https://… with it.

$ pkgcache run -- git clone \https://github.com/pallets/click.git

Model weights, toolchain tarballs, your own build outputs — anything with a URL and no package manager behind it.

new here? two commands

Install it, then tell it how much disk it may use.

pkgcache will not start without a budget, because a cache that grows until the disk is full is a cache that breaks the machine it was meant to help. Give it a number — pkgcache setup -limit 25G — and nothing else is required. The tutorial covers the rest: Docker, a team cache, projects, and carrying the whole thing onto a machine with no network.

and when there is a cache in front of you

Put your team's pkgreg behind it. Nothing else changes.

A team cache is pkgreg — the same engine, run as a host other machines point at. Tell pkgcache about it once and you get three tiers: this machine answers first, the team cache answers what this machine has never seen, and only the team cache talks to the internet. Your commands do not change, because they were already pointed at loopback.

01

This machine

Everything it already holds is served from disk at loopback speed, with nothing crossing the network at all.

02

The team cache

A miss goes to pkgreg, which has probably already fetched it for a colleague. It is verified by CA fingerprint, pinned at setup.

03

Upstream, once

Only what nobody has ever asked for reaches pypi.org or Docker Hub — and -no-direct says even that must go through the team.

ONCEpkgcache setup -server https://cache.internal:8443 -ca-sha256 AA:BB:… -limit 25G
THENevery tool keeps talking to 127.0.0.1; the chain behind it is the only thing that changed
OR-no-cache — a pure client with no local cache, which is what pkgreg-client used to be

The fingerprint comes from whoever runs the cache; it is what makes the first connection safe without installing a CA on this machine. The tutorial's team cache section covers projects, per-project chains, and how to undo all of it.

it is not only a command line

A window, a status-bar item, and a console — all on this machine.

The installers carry a desktop app beside the daemon. It watches the cache that is already running: what it holds, what it saved, whether it is still caching. Nothing here is a service you deploy or a page anyone else can open — it is bound to loopback and refuses to be anything else.

  • The window — pkgcache widget, or the app: size against the budget, hit rate, what arrived recently.
  • The status bar — pkgcache tray keeps a small item beside the clock, and -on-login starts it with your session.
  • The console — pkgcache console opens the full view in your browser, on 127.0.0.1, for the times a number is not enough.
  • Or none of it — pkgcache status prints the same figures and exits, which is what a CI runner wants.

The window beside this is a real screenshot, not a link: everything the app shows lives on the machine running the cache, so there is nothing here for a website to open. The tutorial has a second one, of the same cache a moment earlier, fetching.

every platform, every binary

Download it.

On Debian and Ubuntu there is nothing to download: install it by name from the signed apt repository below, and apt upgrade keeps it current. Everywhere else it is a file — installers for macOS and Windows; static binaries for five targets; the desktop app, the docker shim, the loopback bridge and the pkgreg server beside them. Two channels: a tagged release with a fixed version, and the build of every merge to main. Both are unsigned — there is no Apple or Windows signing identity behind them — so the tutorial has the one extra step macOS and Windows each ask for on first run.

Debian and Ubuntu

Install it by name

A signed repository, so there is nothing to download here and nothing to download again later — apt upgrade moves the machine to each new release. pkgcache-desktop brings the daemon, the CLI, the docker shim and the app; pkgcache on its own is what a server or a CI runner wants, with no desktop graphics stack behind it. 

curl -fsSL https://aabdlwahab.github.io/PKGCache/apt/pkgcache-archive-keyring.asc \
  | sudo tee /usr/share/keyrings/pkgcache-archive-keyring.asc >/dev/null
sudo tee /etc/apt/sources.list.d/pkgcache.sources >/dev/null <<'EOF'
Types: deb
URIs: https://aabdlwahab.github.io/PKGCache/apt
Suites: stable
Components: main
Signed-By: /usr/share/keyrings/pkgcache-archive-keyring.asc
EOF
sudo apt update && sudo apt install pkgcache-desktop
