The shared-cache problem

Every build host re-downloads the internet. Then the air gap takes it away.

Between a handful of CI machines and a locked-down deployment, package fetching quietly becomes the bottleneck — and running four different cache daemons doesn't fix it.

the re-download

Multi-GB torch wheels, every single build

CI pulls the same layers and wheels on every run. Bandwidth burns, builds crawl, and the upstream rate-limits you at the worst moment.

the polyglot zoo

zot + Verdaccio + devpi + apt-cacher-ng

Four upstream projects in Go, Node, Python and C++ — four images, four configs, four ways to break. Nobody owns the whole thing.

the air gap

“Just copy the packages across”

The offline host needs exactly what you cached — no more, no less — and a way to prove it. A folder of tarballs on a USB stick is not a plan.

Six ecosystems · one process · one port

Point every build tool at the same host. It just caches.

Everything HTTPS lives on :8443; apt/apk keep a plain-HTTP proxy on :3142. The cache fills on first request and serves from disk forever after.

The one pull-through path

A hit serves from disk. A miss streams once — to everyone.

Every ecosystem implements one Repository contract over shared primitives. Build the cache once; reuse it everywhere.

01

Content-addressed store

Blobs land at blobs/sha256/… via atomic temp → fsync → rename, so a checkpoint can hash the cache live and HTTP Range comes free.

02

Single-flight streaming

The first requester leads — it tees the upstream to disk and to the client, and finishes even if that client drops. Followers tail the same file. One fetch, ever.

03

Per-ecosystem ledger

A native SQLite ledger records every artifact as it's cached — so you always know exactly what a checkpoint contains, and offline can resolve tags and refs.

live GET a package
HITpresent on disk → FileResponse (200 / 206 Range)
MISSstream upstream → tee to .part + client → verify sha256 → atomic rename → ledger.record()
FAILnon-2xx is never cached as content — recorded in the recent feed

Versioned & air-gap portable

git + DVC turn the cache into a shippable, rollback-able snapshot.

Each project's cache state lives in its own git + DVC repo, separate from the code. Checkpoint live, export the delta, carry it across, import, serve offline.

  1. onlineCheckpointmanifest → dvc add → git commit — no quiesce, proxies keep serving.
  2. onlineExportdvc push + git bundle of just the delta → shuttle/out/.
  3. carryShuttlecopy out/ onto removable media, walk it across the gap.
  4. offlineImportfrom shuttle/in/: git ff + dvc pull + checkout.
  5. offlineServeOFFLINE=1 — same URLs, cache-only, a miss simply fails.
# online host — version live, then stage just the delta
$ python3 scripts/pkgops.py checkpoint "added numpy 2.1 + torch 2.3"
$ python3 scripts/pkgops.py export --base <sha> --target <sha>   # → shuttle/out/

# air-gapped host — drop the media into shuttle/in/, then
$ python3 scripts/pkgops.py import
$ OFFLINE=1 docker compose --profile offline --profile ui up -d
